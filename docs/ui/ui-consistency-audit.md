# Butlerly UI consistency audit

Status: audit-only evidence for GitHub Issue [#386](https://github.com/Jack84283/Butlerly/issues/386)

Audited revision: `main` at `96ed77d6` (`fix(finance): complete statement intake and evidence recovery (#385)`)

This report makes no production UI change. It records what is implemented, what is inconsistent, and what should be implemented in follow-up PRs.

## Executive summary

Butlerly already has a credible foundation: semantic light/dark theme extensions, centralized spacing/radius/size tokens, a width-driven Compact/Medium/Wide resolver, shared page/card/row primitives, localized UI, and a useful responsive widget-test matrix. The main risk is contract drift around that foundation, not the absence of a design system.

The highest-priority audit result is a decision blocker. Issue #386 preserves light background `#F2F3F9` and light cards `#FDFDFD`, while the current repository authority and tests specify `#F6F7F8` and `#FFFFFF`. The issue also preserves dark background `#030405` and dark cards `#141516`, while the runtime semantic palette currently supplies `#0D0D0D` and `#181818` even though `DESIGN.md` documents the issue’s dark values. The audit does not choose between them. Issue #386 is labeled `needs-decision` and contains the structured clarification.

The recurring implementation problems are:

1. documentation, token, and test contracts are no longer identical (light/dark palettes, button height, wide-navigation width, and one responsive breakpoint statement);
2. repeated feature-owned visual implementations remain alongside shared components (privacy banner, analysis breakdown rows, desktop action cards, status colors, and table widths);
3. responsive tests mostly prove that pages pump without exceptions, not that every UX-0005 state, focus path, semantic name, large-text reflow, or visual contract is correct;
4. screenshot evidence is narrow. Two checked-in mobile PNGs are useful visual anchors, but no `matchesGoldenFile` usage was found. A live iPhone capture remained on the launch surface and produced a black simulator image, so no unverified visual claim is made from it.

Recommended first implementation PR after the baseline decision: reconcile the active light/dark design authority, semantic palette, button/navigation/financial-period contracts, and their contract tests in one small PR. Then extract the repeated privacy/status and analysis-row primitives before migrating individual screens.

## Method and evidence

The audit used:

- Impeccable context resolution and its native-app guidance. The native guidance was followed: browser detector output was not treated as Flutter evidence. The installed CLI does not expose `init`, `document`, `audit`, or `critique` as terminal commands; those are chat-skill commands. The skill reported `.impeccable/design.json` as stale relative to `DESIGN.md`; it was not silently refreshed during this audit.
- Official Flutter/Dart skills for responsive layout, widget testing, and static analysis. The relevant skills were read from the installed Dart/Flutter plugin.
- Flutter source, theme/token code, router, shared components, UI tests, and two checked-in rendered PNG anchors. No `matchesGoldenFile` usage was found in the test tree.
- Dart/Flutter MCP: the macOS app widget tree was inspected through DTD. The iPhone simulator exposed `ButlerlyLaunchSurface` and a startup progress indicator but did not reach the main shell during the inspection window. Runtime errors were empty; the simulator screenshot was black and is treated as a capture limitation, not as visual product evidence.
- [UX-0005 — Butlerly Screen and State Inventory v1.0](https://docs.google.com/document/d/1ythL6tZSoR1KP9SlGnM2f3t9kTKV3x6FbpmUHu3IAWc/edit?usp=drivesdk), version 1.0 and referenced by Issue #386, was the external product source used for the screen/state taxonomy. The `Required audit states` column below is the row-level mapping to that taxonomy; the document has no immutable repository SHA, so its section-level guidance must be pinned and re-verified before implementation. Other Drive documents were consulted only as background; they are not treated as implementation authority because Issue #386 does not pin them and the repository guidance gives active authority to the checked-in documents.

`PRODUCT.md` and `DESIGN.md` were reviewed but intentionally not edited. `DESIGN.md` contains the active implementation values that conflict with the Issue #386 preservation values; updating it in this audit would make the unresolved baseline decision silently. Phase 0 of the migration plan is the appropriate place to update `DESIGN.md`, the semantic palette, tests, and visual baselines together after human review.

## What is already working

- `ButlerlySemanticColors` provides a real ThemeExtension with dedicated roles for surfaces, text, borders, interaction, status, selection, and review.
- `ButlerlySpacing`, `ButlerlyRadius`, `ButlerlySize`, sheet/table/button tokens, and responsive geometry provide a strong base for consolidation.
- `ButlerlyResponsiveDesignTokens.of` is width-driven and uses `MediaQuery.sizeOf`; tablet-landscape promotion is explicit (`apps/butlerly/lib/design_system/theme/butlerly_responsive_design_tokens.dart:29-55`).
- Shell tests cover Compact, Medium, Wide, rotation, Android, and navigation semantics (`apps/butlerly/test/app/responsive_shell_test.dart:280-329` and surrounding cases).
- The UI gap matrix deliberately combines narrow phone, dark Spanish, large-text Chinese, and medium-width Chinese cases (`apps/butlerly/test/app/ui_gap_responsive_test.dart:19-24`).
- Existing shared month picker, modal sheet, action group, content surface, transaction controls, transaction row, category icon, and desktop table components are good extraction anchors.
